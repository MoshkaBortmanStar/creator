# OpenSpec Change Driver — работа через движок

В этом проекте фичи проходят через жёсткий конвейер:
`MAIN.md → --new (proposal → spec-bdd → tasks) → --codegen (тесты → код)`.

Движок — установленная команда `openspec` (пакет openspec-driver). Он сам
вызывает LLM по своим промптам и пишет артефакты на диск. Твоя роль —
оркестрация, ревью и доводка, а НЕ ручная генерация артефактов.

Движок лежит ВНЕ проекта и находит его сам по `.agent/config.yaml` вверх
от текущего каталога. Копий движка в репозитории проекта нет и быть не должно.

## Шаг 0. Проверка движка

Движок запускается обёрткой из корня проекта:

```bash
./openspec --list
```

Разбор ответов:

- Печатает профиль и список изменений → работай по шагам ниже.
- `./openspec: No such file or directory` → проект не развёрнут. Движок
  подключается submodule'ом, затем разворачивается:
  ```bash
  git submodule add /Users/mikhailbutorin/programmer/creator .openspec
  uvx --from ./.openspec openspec --init
  ```
- `Движок не найден: .../.openspec пуст` → репозиторий клонирован без
  submodule: `git submodule update --init .openspec`
- `Не найден uvx` → `brew install uv`
- «Это не проект OpenSpec» → submodule есть, а конфига нет:
  `uvx --from ./.openspec openspec --init`

Все команды движка вызывай через `./openspec`, а не `openspec`: движок
не установлен в систему, он живёт в submodule проекта.

Ручную генерацию артефактов начинай только с явного разрешения пользователя.

## Рабочий процесс

### Пользователь просит фичу («хочу...», «добавь...», «нужно...»)

1. Если фича неясна — сначала коротко уточни (1–3 вопроса, стиль
   brainstorming-скилла). НЕ начинай генерацию по сырой двусмысленной мысли.
2. Если `specs/MAIN.md` отсутствует — предложи сначала
   `--main "что за приложение"` (контекст для всех генераций).
3. Запусти конвейер:
   ```bash
   ./openspec --new "<уточнённый промпт>"
   ```
4. Прочитай созданный `specs/<change-id>/spec-bdd.md` и покажи пользователю
   краткое резюме сценариев (S1..Sn) — НЕ вываливай файл целиком.
5. Пользователь правит спеку (руками или через тебя) → при сильных правках:
   ```bash
   ./openspec --tasks --change <ID>   # перегенерить план
   ```

### Кодогенерация

```bash
./openspec --codegen --change <ID> --dry-run   # посмотреть
./openspec --codegen --change <ID>             # записать (спросит y/N)
```

После записи — прогони тесты (`mvn test` / аналог из стека). Если падают:
дожимай код сам в стиле TDD-скилла, спека уже описывает ожидаемое поведение.

## Шпаргалка команд

| Команда | Назначение |
|---|---|
| `--main "описание"` | создать/обновить мейн-спеку `specs/MAIN.md` |
| `--new "промпт"` | полный конвейер: proposal + spec-bdd + tasks |
| `--spec/--tasks/--proposal --change <ID>` | перегенерация одного артефакта |
| `--codegen --change <ID>` | код по спеке и таскам |
| `--list` / `--status [--change ID]` | список изменений / статусы |
| `--offline` | каркасы без LLM |
| `--model NAME` / `--profile alfagen\|local` | выбор модели/провайдера разово |
| `--new "промпт" --worktree` | спека + коммит + отдельный git worktree под изменение |
| `--worktrees` | список worktree: ветка, база, что не смерджено |

`<ID>` можно сокращать: полный `change-002-...`, префикс `change-002` или номер `2`.

## Параллельная работа над изменениями (worktree)

Если у пользователя **уже есть незавершённое изменение** (проверь `--worktrees`
или `--status`) и он просит начать ещё одно — **спроси, создавать ли worktree**:

> «Change-002 ещё в работе. Создать для новой фичи отдельный worktree,
> чтобы вести их параллельно?»

Ответил «да» — добавляй флаг `--worktree` к `--new`.

Что делает флаг: генерит артефакты → **коммитит папку спеки в текущую ветку**
→ создаёт `../<Проект>-wt-<NNN>` с веткой `change/<NNN-slug>` от этого коммита.
Путь и ветка пишутся в `change.yaml` (секция `git`).

Порядок «сначала коммит, потом worktree» принципиален: номер изменения
выдаётся по максимуму папок в `specs/`, и два worktree от одного коммита
выдали бы одинаковый ID.

### Где запускать кодоген

**Кодоген запускай из основной директории — движок сам разберётся.**

Порядок внутри `--codegen`:

1. Нет привязанного worktree → **создаёт его** (коммитит спеку, заводит ветку
   `change/<NNN-slug>`). Отключается `pipeline.auto_worktree: false`.
2. Worktree есть → читает путь из `change.yaml` и **перезапускает себя там**
   с теми же аргументами.

Вручную ничего создавать и никуда переходить не нужно — ни `--worktree`,
ни `cd`.

**Важно про незакоммиченное.** Worktree отпочковывается от коммита, поэтому
незакоммиченные файлы вне `specs/` в него НЕ попадут. Движок это проверяет:
находит такие файлы — показывает список и спрашивает подтверждение. Увидел
такой вопрос — не отвечай «да» автоматически: сообщи пользователю список
и предложи сначала закоммитить.

**Файлы вне git** (`local.properties`, `.env`) копируются в новый worktree
автоматически — список в `pipeline.worktree_copy`. Если тесты в worktree
падают из-за окружения, а не кода (нет SDK, нет переменных сборки) — это
значит, что нужного файла нет в списке: допиши его в конфиг, а не чини
worktree руками.

Флаг `--here` отключает переход (генерировать в текущей директории) — нужен
редко, предлагай только если пользователь явно просит.

### Батчи: длинные планы генерируются порциями

Если задач в `tasks.md` больше, чем `code_generation.batch_size` (по умолчанию 3),
движок сам разбивает работу: каждый батч — отдельный запрос со своими задачами
плюс уже созданные файлы как контекст, результат пишется на диск **сразу**.

Это не опция для особых случаев, а обычный режим. Ничего специально включать
не нужно. Разово изменить размер: `--batch N`, целым планом: `--batch 0`.

**Прерванный кодоген продолжается, а не начинается заново.** После каждого
батча прогресс пишется в `change.yaml` (секция `codegen`). Повторный запуск
пропускает готовые батчи и поднимает их контекст с диска — файлы там уже
лежат. Поэтому НЕ перезапускай кодоген «чтобы было консистентно»: просто
запусти ту же команду, он продолжит с места обрыва. Нужна полная
перегенерация — флаг `--fresh`.

Прогресс считается годным, только если план и `batch_size` не менялись.
Перегенерировал `tasks.md` — движок сам начнёт с начала.

Следствие для тебя: кодоген по плану на 12 задач — это 4 запроса и несколько
минут. Не считай это зависанием и не перезапускай.

### Зависимости добавляются сами

Файлы сборки из `code_generation.dependency_files` уходят в промпт с актуальным
содержимым, и модели прямо предписано: нужна библиотека, которой нет — добавь
и выведи файл сборки целиком отдельным `### FILE`.

Поэтому НЕ добавляй зависимости руками до кодогена. Если после прогона тесты
падают на нерешённом импорте — значит модель зависимость пропустила: добавь её
сам и перезапусти тесты, а не весь кодоген.

### Что кодоген делает сам

После записи файлов движок продолжает автоматически, в той же директории:

1. Прогоняет тесты командой `code_generation.test_command` из config.yaml
2. Зелёные **и** изменение живёт в своём worktree → коммитит `feat: <change-id>`
   и печатает команду мерджа
3. Красные → коммита нет, файлы остаются в рабочем дереве

Флаги: `--no-test` (пропустить прогон), `--no-commit` (не коммитить).

Значит после успешного кодогена делать ничего не нужно — скажи пользователю,
что изменение готово к мерджу, и покажи вывод.

Если тесты упали — дожимать надо **внутри worktree**: правки файлов и повторный
прогон движок не перенаправляет. Скажи пользователю открыть сессию в этом
worktree, там почини и закоммить.

Правила:

- **Спеки генерируются только в основном worktree.** В дочерних — кодоген,
  тесты, правки. Иначе номера снова разъедутся.
- Перед началом работы предложи пользователю завести ветку задачи
  (`git checkout -b feature/<имя>`) — worktree ответвятся от неё, и мерджить
  всё нужно обратно в неё.
- Разводи параллельные изменения так, чтобы они **не трогали одни файлы** —
  спеки не конфликтуют (разные папки), а код конфликтует как обычно.
- Закончил изменение — покажи пользователю команды мерджа и уборки:
  `git merge <ветка>`, `git worktree remove <путь>`, `git branch -d <ветка>`.
- Перед тем как объявить работу завершённой, прогоняй `--worktrees`:
  если что-то не смерджено — скажи об этом явно.

## Правила экономии токенов

- Вывод скрипта уже содержит всё нужное (пути артефактов) — не перечитывай
  файлы без необходимости.
- Читай `spec-bdd.md` только на ревью; `tasks.md` — перед кодогенерацией.
- НЕ копируй содержимое артефактов в ответ целиком — резюмируй.

## Принципы

- Спека важнее кода: несоответствие кода спеке = чинить код (или спеку
  осознанно, с явного согласия пользователя).
- Код без спеки не пишем. Прежде чем кодить фичу — проверь, есть ли change-*;
  нет — предложи `--new`.
- Перед `--codegen` покажи пользователю план из `tasks.md`, а не гоняй
  `--dry-run`: это полная генерация впустую.
