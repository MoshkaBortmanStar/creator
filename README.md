# OpenSpec Change Driver

> **MAIN Spec (что за приложение) → Промпт → Proposal → BDD Spec (GIVEN-WHEN-THEN) → Tasks → Код**
>
> Локальный CLI-движок подхода Spec-Driven Change Development: описывает
> приложение в мейн-спеке, превращает абстрактный промпт («хочу эхо-сервис
> с кодированием в base64») в структурированную документацию — предложение,
> BDD-спецификацию, план задач — и генерирует по ней Java/Spring Boot код
> через LLM. Полностью дженерик: любой промпт → своя спека, любой стек в
> конфиге → свой код.

## 1. Как это работает

Движок — это жёсткий конвейер. **Первичный документ — мейн-спека**
(`specs/MAIN.md`): что за приложение, зачем, какой стек. Она описывается
один раз командой `--main` и **автоматически подмешивается в контекст
каждого шага** — все изменения генерируются с пониманием, в каком проекте
они происходят.

Дальше каждое изменение (Change) — конвейер из 4 шагов. Каждый шаг создаёт
**артефакт** (файл в `specs/<change-id>/`), и каждый следующий шаг
использует предыдущие как контекст. Правила шагов описаны в
`.agent/schema.yaml` — скрипт читает их оттуда, а не зашивает в код.

```
                 specs/MAIN.md  ← мейн-спека: что за приложение, какой стек
                        │  (контекст для ВСЕХ шагов ниже)
                        ▼
сырой промпт пользователя
        │
        ▼
┌─────────────────┐    ┌──────────────────┐    ┌───────────────┐    ┌──────────────────┐
│ 1. proposal.md  │───▶│ 2. spec-bdd.md   │───▶│ 3. tasks.md   │───▶│ 4. КОД           │
│ Зачем? Что      │    │ GIVEN-WHEN-THEN  │    │ микро-задачи  │    │ .java файлы      │
│ меняется?       │    │ + OpenAPI Delta  │    │ (≤ 2 часа)    │    │ тесты → реализация│
└─────────────────┘    └──────────────────┘    └───────────────┘    └──────────────────┘
  до 100 слов           все краевые случаи     первая задача —      MockMvc-тесты
                                                падающий тест       + контроллеры/сервисы
```

Ключевые принципы (заложены в системные промпты и правила схемы):

- **MAIN Spec** — первичный документ: что за приложение и какой стек.
  Создаётся командой `--main`, подмешивается во все шаги конвейера.
- **Proposal** отвечает на «Зачем», а не «Как». Максимум 100 слов.
- **Spec** — строгий синтаксис GIVEN / WHEN / THEN + обязательные краевые
  случаи (валидация, ошибки 400, 500) + дельта OpenAPI-контракта.
- **Tasks** — декомпозиция на задачи не более 2 часов; первой задачей
  всегда идёт создание падающего теста (TDD).
- **Кодогенерация** идёт тест-первым: сначала MockMvc-тесты, воспроизводящие
  сценарии спеки, затем реализация, чтобы тесты позеленели.

## 2. Структура проекта

```
creator/                            ← корень твоего проекта
├── .agent/                         ← движок (можно переносить между проектами)
│   ├── templates/                  ← шаблоны артефактов
│   │   ├── main.template           ←   структура MAIN.md (мейн-спека)
│   │   ├── proposal.template       ←   структура proposal.md
│   │   ├── spec.template           ←   структура spec-bdd.md (BDD + OpenAPI)
│   │   └── tasks.template          ←   структура tasks.md
│   ├── config.yaml                 ← настройки: стек проекта, LLM, пайплайн
│   ├── schema.yaml                 ← мета-правила конвейера (шаги и артефакты)
│   └── (больше ничего — движок установлен в систему, команда openspec)
├── .opencode/                      ← агентный слой opencode (переносится вместе с .agent)
│   ├── skills/                     ← скиллы Superpowers (14 шт) + openspec-driver
│   └── command/                    ← команды /openspec-new, /openspec-codegen
├── specs/                          ← сгенерированные спецификации
│   ├── MAIN.md                     ← МЕЙН-СПЕКА: что за приложение, какой стек
│   │                                  (первичный документ, контекст для всего)
│   └── change-001-base64-echo/     ← ПРИМЕР: одно изолированное изменение
│       ├── change.yaml             ←   метаданные (промпт, даты, статусы)
│       ├── proposal.md             ←   зачем и что меняется
│       ├── spec-bdd.md             ←   сценарии GIVEN-WHEN-THEN + OpenAPI Delta
│       └── tasks.md                ←   пошаговый план с чек-боксами
└── src/main/java/...               ← целевой код приложения (генерируется сюда)
```

> `specs/change-001-base64-echo/` — это живой демо-пример, созданный вручную.
> Посмотри его файлы — это образец того, что генерирует движок.

## 3. Установка

Движок **не ставится ни на машину, ни в проект**. Он лежит в git, а `uvx`
собирает его на лету и держит в своём кеше. В проекте от движка остаётся
один файл — обёртка `openspec.py` с адресом репозитория.

Что это даёт:

- **изоляция** — ничего не попадает ни в системный python, ни в `PATH`,
  ни в репозиторий проекта;
- **версия задаётся строкой** в обёртке: `@master`, тег или SHA — на выбор,
  и лежит она в истории твоего проекта;
- **воспроизводимость** — коллега клонирует репозиторий, и у него тот же
  движок, что у тебя.

### Единственное требование к машине — uv

```bash
brew install uv                    # macOS / Linux
```

```
winget install astral-sh.uv        # Windows
```

Это один самодостаточный бинарник. Python для движка `uv` скачает себе сам —
системный не нужен и не трогается.

> ### Руками — одна команда, один раз на проект
>
> ```bash
> uvx --from git+https://github.com/MoshkaBortmanStar/creator.git@master openspec --init
> ```
>
> Она разворачивает проект и создаёт обёртку. **Дальше руками ничего
> вводить не нужно** — всё остальное делается через opencode, а если удобнее
> терминал, то через `./openspec.py ...`. Ниже у каждого шага показаны
> все способы.
>
> #### Как обращаться к opencode
>
> | Способ | Пример | Когда |
> |---|---|---|
> | **обычными словами** | `сделай спеку на экспорт заказов в CSV` | основной; агент поймёт по скиллу |
> | **слэш-командой** | `/openspec-new экспорт заказов в CSV` | когда хочешь наверняка |
> | **в терминале** | `./openspec.py --new "..."` | когда удобнее руками |
>
> Словесная форма работает потому, что `--init` кладёт в проект скилл
> `openspec-driver`. Агент видит его описание — там перечислены слова-триггеры
> («спека», «change», «кодогенерация») и признак «в проекте есть `specs/`» —
> и сам решает применить конвейер. Это **вероятностный** механизм: обычно
> срабатывает, но модель может и не связать твою фразу с навыком.
>
> Слэш-команда **детерминирована**: opencode берёт файл
> `.opencode/command/openspec-new.md`, подставляет твой текст и отправляет
> как промпт. Никаких догадок. Таких команд две — `/openspec-new`
> и `/openspec-codegen`; для остального пиши словами.

### Шаг 1. Развернуть проект

**Через opencode:**

```
разверни openspec в этом проекте
```

**Напрямую**, из корня проекта:

```bash
uvx --from git+https://github.com/MoshkaBortmanStar/creator.git@master openspec --init
```

**Что делает:** разбирает проект в два прохода и создаёт всё нужное.

**Проход 1 — по файлам сборки** (быстро, без сети):

```
Определено по build.gradle.kts:
  tech_stack           Spring Boot (WebFlux), Coroutines, Kotlin, JUnit 5
  base_package         bortman.co.echoservertest
  source_root          src/main/kotlin
  test_command         ./gradlew test
  dependency_files     build.gradle.kts
  project_map_roots    src/main/kotlin, src/test/kotlin
```

Распознаются Gradle (включая Android с модулем `app`), Maven, Python, Node,
Go, Rust. Команда тестов подбирается под ОС: на Windows будет `gradlew.bat`,
а не `./gradlew`.

**Проход 2 — чтением кода моделью.** Движок собирает обзор проекта (файлы
сборки целиком плюс дерево исходников с объявлениями) и просит модель
описать стек и архитектурный стиль словами:

| | результат |
|---|---|
| проход 1 | `Spring Boot, Coroutines, Kotlin, JUnit 5, Flyway, SQLite` |
| проход 2 | `Kotlin 2.3.21 (toolchain Java 21), Spring Boot 4.1.1 (web, jdbc, flyway), SQLite, bcrypt/argon2, OpenAPI Generator 7.14.0…` |
| `code_style` | `слоистая controller → service → repository, без JPA — plain JDBC; DTO из OpenAPI; корутины вместо реактивных типов; тесты интеграционные (*IT, WebTestClient)` |

Второй проход необязательный: нет ключа, нет сети, модель не ответила —
`--init` доживёт до конца на результатах первого и скажет, что пропустил.
Отключить заранее: `--offline`.

### Что создаёт `--init`

| Файл | Кто читает | Зачем |
|---|---|---|
| `.agent/config.yaml` | движок | стек, профиль, команда тестов |
| `specs/` | движок | артефакты конвейера |
| `openspec.py` | ты | запуск движка, в нём же задана версия (в `.gitignore`) |
| `.opencode/skills/` (15 штук), `.opencode/command/` | агент | конвейер плюс библиотека навыков (в `.gitignore`) |
| `AGENTS.md` | агент | правило точечных правок вместо перепечатывания файлов (в `.gitignore`) |

Существующие файлы не перезаписываются: если `AGENTS.md` у команды свой,
`--init` его не тронет.

**Про `AGENTS.md` и экономию токенов.** Правило «правь диффами, не
переписывай файл целиком» действует в двух местах и обеспечивается
по-разному:

| Кто правит код | Чем управляется |
|---|---|
| агент (opencode) своими руками | `AGENTS.md` в корне проекта |
| движок на шаге `--codegen` | промпт движка: он требует блоков `<<<<<<< SEARCH / >>>>>>> REPLACE` для существующих файлов |

То есть движок `AGENTS.md` **не читает** — у него своё, более жёсткое
требование внутри промпта.

### Как запускать

Обёртка — обычный python-скрипт, поэтому команда чуть разная:

| Платформа | Команда |
|---|---|
| macOS, Linux | `./openspec.py --codegen --change 1` |
| Windows | `python openspec.py --codegen --change 1` |

Один файл вместо пары `bash` + `.cmd` намеренно: внутри есть проверки
и сообщения об ошибках, и держать их в двух копиях — верный способ
однажды поправить только одну.

### Скиллы агента: 15 штук, локально в проекте

`--init` разворачивает в `.opencode/skills/` не только `openspec-driver`,
но и библиотеку общих навыков:

| Группа | Скиллы |
|---|---|
| конвейер | `openspec-driver` |
| качество | `test-driven-development`, `systematic-debugging`, `verification-before-completion` |
| ревью | `requesting-code-review`, `receiving-code-review` |
| планирование | `writing-plans`, `executing-plans`, `brainstorming` |
| git | `using-git-worktrees`, `finishing-a-development-branch` |
| субагенты | `dispatching-parallel-agents`, `subagent-driven-development` |
| прочее | `using-superpowers`, `writing-skills` |

**Почему в каждом проекте, а не глобально.** opencode читает скиллы ровно
из двух мест: корень проекта и `~/.config/opencode/skills/`. Вглубь он не
сканирует. Раскладка по проектам даёт изоляцию: на машине ничего не оседает,
у каждого проекта свой набор, обновляется он вместе с движком.

> **Windows.** Четыре скилла содержат вспомогательные скрипты на bash
> (`brainstorming`, `systematic-debugging`, `subagent-driven-development`,
> `writing-skills`). Сами инструкции работают везде, но если агент полезет
> в эти скрипты — на родной Windows они не запустятся. В WSL работают.

### Что уходит в git, а что нет

| Файл | В git | Почему |
|---|---|---|
| `.agent/config.yaml` | **да** | общие настройки: стек, команда тестов, раскладка исходников |
| `specs/` | **да** | продукт работы и история решений |
| `openspec.py` | нет | генерируется `--init` одинаковым у всех |
| `.opencode/`, `AGENTS.md` | нет | инструкции агенту, разворачиваются `--init` локально |

Граница: в репозиторий уходит только то, что **нельзя получить заново** —
конфиг проекта и спеки. Всё, что `--init` создаёт из данных пакета, каждый
разворачивает у себя той же командой.

Файлов движка в репозитории **нет вообще**.

### Шаг 3. Прописать ключ

**Ключ живёт только в переменной окружения.** В `config.yaml` его класть
нельзя — движок откажется работать и скажет почему. Причина: конфиг уходит
в git, а секрет из истории коммитов потом не вычистить — недостаточно
убрать строку из текущей версии файла, старый коммит всё помнит.

Поэтому в конфиге указано только **имя переменной**:

```yaml
profiles:
  glm:
    api_key_env: "ZAI_API_KEY"    # имя переменной, НЕ сам ключ
```

Где взять сам ключ: в личном кабинете Z.AI (подписка Coding Plan).

```bash
echo 'export ZAI_API_KEY="..."' >> ~/.zshenv
```

**Обязательно `~/.zshenv`, а не `~/.zshrc`.** Разница неочевидная и стоила
нам часа отладки: `~/.zshrc` читается только когда ты сам открыл терминал.
Движок, запущенный из IDE или скрипта, работает в неинтерактивной оболочке —
она `~/.zshrc` не читает, переменная окажется пустой, и ты получишь `401`
с непонятной причиной. `~/.zshenv` читают **все** оболочки.

На Windows — через переменные среды пользователя или:

```
setx ZAI_API_KEY "..."
```

Перезапусти терминал и проверь:

```bash
echo ${ZAI_API_KEY:+ключ на месте}
```

Что провайдер отвечает:

```bash
curl -k -s -o /dev/null -w "HTTP %{http_code}\n" \
  -X POST https://api.z.ai/api/coding/paas/v4/chat/completions \
  -H "Authorization: Bearer $ZAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"glm-5.3","messages":[{"role":"user","content":"ping"}],"max_tokens":5}'
```

`200` — готово. `401` — ключ. `404` — имя модели или endpoint: у Coding Plan
путь `/api/coding/paas/v4`, обычный `/api/paas/v4` с ключом подписки не работает.

Проверяй именно `/chat/completions`: `/models` отвечает и без
валидного ключа, как проверка он бесполезен.

### Шаг 4. Проверить то, что машина знать не может

| Поле в `.agent/config.yaml` | Что это | Обязательно? |
|---|---|---|
| `active_profile` | каким провайдером генерировать: `glm` или `local` | **да** |
| `code_style` | договорённости именно вашей команды | желательно |
| `tech_stack` | проверить, что модель не приписала лишнего | желательно |

Профили уже прописаны — они приезжают из репозитория движка, руками их
создавать не надо. Выбор один: какой активен.

```yaml
active_profile: "glm"     # или "local" — локальная модель без сети
```

Всё. Дальше — `./openspec.py --main "..."` и обычный цикл.

## 3.2. Обновление движка

Версия задана **одной строкой** в `openspec.py`:

```python
ENGINE = "git+https://github.com/MoshkaBortmanStar/creator.git@master"
```

| Что указать | Поведение |
|---|---|
| `@master` | всегда свежий движок; меняется сам, когда кто-то пушит |
| `@v0.5.0` | зафиксировано тегом; обновление — осознанная правка строки |
| `@9b1d305` | зафиксировано коммитом намертво |

Сейчас стоит `@master`. Это удобно, пока проект один, но помни: движок
может измениться между двумя твоими запусками, и для резолва ветки нужна
сеть при каждом вызове. Понадобится стабильность — поменяй на тег
и закоммить; строка одна, у всех в проекте станет одинаково.

Посмотреть, что запущено:

```bash
./openspec.py --version
```

```
openspec-driver 0.4.0
  движок:  /Users/.../.cache/uv/archive-v0/.../openspec_driver
  проект:  /Users/.../мой-проект
```

> Если в проекте висит незавершённая кодогенерация (секция `codegen:`
> в `change.yaml`), доведи её до конца или запусти заново с `--fresh`
> перед сменой версии: формат прогресса между версиями может измениться.

## 3.3. Настроить LLM и модель



Движок работает с **любым OpenAI-совместимым API**. Провайдер задаётся
профилем в `.agent/config.yaml`:

| Провайдер | `base_url` | `model` | Ключ |
|---|---|---|---|
| **Z.AI Coding Plan** (по умолчанию) | `https://api.z.ai/api/coding/paas/v4` | `glm-5.3` | `ZAI_API_KEY` |
| **Ollama** (локально, бесплатно) | `http://localhost:11434/v1` | `qwen2.5-coder:7b` | не нужен |
| **OpenAI** | `https://api.openai.com/v1` | `gpt-4o` | `OPENAI_API_KEY` |
| **OpenRouter** | `https://openrouter.ai/api/v1` | `anthropic/claude-sonnet-4` | `OPENROUTER_API_KEY` |

> **У Z.AI Coding Plan отдельный endpoint** — `/api/coding/paas/v4`.
> Обычный `/api/paas/v4` это pay-as-you-go, ключ подписки там **не работает**
> и вернёт `401`.

### Как быстро поменять модель

**Способ 1 — навсегда (правка конфига).** Модель живёт в профиле:

```yaml
profiles:
  glm:
    base_url: "https://api.z.ai/api/coding/paas/v4"
    model: "glm-5.3"          # ← поменяй здесь
```

| Модель | Для чего |
|---|---|
| `glm-5.3` | **по умолчанию** — универсальная, тянет и спеки, и код |
| `glm-4.6` | предыдущее поколение, дешевле по лимиту |

Актуальный список — в личном кабинете Z.AI: набор моделей в подписке
меняется, а обращение к исчезнувшей даёт `404`.

**Про размышления.** GLM — думающая модель: сначала генерирует рассуждения,
потом ответ, и `max_tokens` у них **общий**. На кодогенерации это приводило
к пустым ответам после нескольких минут работы. Отключается в
`code_generation.extra_params` — см. раздел про `extra_params`.

**Способ 2 — на один запуск (флаг `--model`), без правки конфига:**

```bash
# спеку одной моделью, а код другой:
./openspec.py --new "хочу поиск по заказам" --model glm-5.3
./openspec.py --codegen --change 2 --model glm-4.6
```

Флаг переопределяет `model` из конфига только для текущей команды.

**Способ 3 — сменить провайдера целиком.** Провайдер задаётся **только
профилем**. В `config.yaml` есть секция `profiles` и одна строка, выбирающая
активный:

```yaml
active_profile: "glm"   # поменял здесь — сменилось во всём конвейере
```

В корпоративном контуре доступны два профиля:

| Профиль | Что это | Когда |
|---|---|---|
| `glm` | Z.AI Coding Plan | по умолчанию |
| `local` | локальная Ollama | когда нет сети |

`base_url`, `model` и ключ живут внутри профиля и больше нигде: в
`ai_settings` остались только параметры, от провайдера не зависящие
(`temperature`, `max_tokens`, `timeout_seconds`, `stream`, `extra_params`).

**Способ 4 — профиль на один запуск**, не трогая файл:

```bash
./openspec.py --new "..." --profile local            # локальная модель
./openspec.py --codegen --change 2 --profile glm  # рабочий шлюз
```

Приоритет: `--model` > `--profile` > `active_profile`.

Профиль **обязателен**: если ни `active_profile`, ни `--profile` не заданы,
скрипт падает с явной ошибкой и списком доступных профилей. Дефолтов у
`base_url` и `model` нет намеренно — иначе движок молча ушёл бы на чужой
хост. Активный профиль печатается в начале каждого запуска:

```
Профиль 'glm': model=glm-5.3, base_url=https://api.z.ai/api/coding/paas/v4
```

### Добавить свой профиль (внешний провайдер)

Из корпоративной сети внешние API недоступны, но эта же репа может работать
и вне контура. Новый провайдер добавляется правкой конфига, без кода —
допиши блок в `profiles` и переключись на него:

```yaml
profiles:
  # ... glm и local ...

  glm:                                   # Z.AI Coding Plan
    # У Coding Plan свой endpoint — /api/coding/paas/v4.
    # Обычный /api/paas/v4 — pay-as-you-go, ключ подписки там не работает.
    base_url: "https://api.z.ai/api/coding/paas/v4"
    model: "glm-5.3"
    api_key_env: "ZAI_API_KEY"
    verify_ssl: true

  openai:
    base_url: "https://api.openai.com/v1"
    model: "gpt-4o"
    api_key_env: "OPENAI_API_KEY"
    verify_ssl: true
```

Требования к профилю: обязательны `base_url` и `model`, API должен быть
**OpenAI-совместимым** (`POST /chat/completions`). Ключ — **только** через
`api_key_env`, никогда строкой в файле: конфиг уходит в git, а секрет в
истории коммитов остаётся навсегда, даже если убрать его из текущей версии.

Для кодогенерации Java настоятельно рекомендую **модель-кодер** —
модель посильнее: универсальные модели среднего размера часто выдают
неполные файлы — обрывают их на середине или молча пропускают задачи
из плана.

### Проверить, что всё живо

```bash
./openspec.py --list
```

Печатает активный профиль и список изменений — значит движок нашёл проект
и готов к работе.

### Шаг 1. Создаём изменение: `--new`

```bash
./openspec.py --new "хочу эхо-сервис с кодированием в base64"
```

Что делает скрипт:

1. Придумывает ID: `change-002-base64-eho-servis` (порядковый номер +
   slug из промпта, кириллица транслитерируется).
2. Создаёт папку `specs/change-002-.../` и пишет в неё `change.yaml`
   (промпт, дата, статусы артефактов).
3. **Трижды вызывает LLM** — по разу на каждый артефакт, и каждый раз
   **сначала подмешивает MAIN.md** (что за приложение и стек):
   - `proposal.md` — системный промпт «AI Архитектор», правила из
     `schema.yaml` (≤ 100 слов, фокус на «Зачем»), структура из шаблона;

   - `tasks.md` — на вход получает **proposal + spec** + правила
     (задачи ≤ 2 часа, первая задача — падающий тест).
4. После каждого артефакта обновляет статус в `change.yaml`.

```

Дальше:

| Команда | Что делает |
|---|---|

### Флаги-модификаторы

| Флаг | С чем работает | Что делает |
|---|---|---|
| `--offline` | `--main`, `--new`, `--proposal`, `--spec`, `--tasks` | Не вызывать LLM — создать каркасы по шаблонам с `TODO` |

- префикс: `change-001`
- **номер: `1`**

## 7. Спеки: MAIN.md и BDD (GIVEN-WHEN-THEN)

В проекте два вида спек: **мейн-спека** (одна на проект) и **BDD-спеки
изменений** (по одной на каждый change).

### 7.1 Мейн-спека проекта — `specs/MAIN.md`

Первичный документ: **что за приложение и какой у него стек**. Секции:

- `What Is This App` — что за продукт, для кого, какую проблему решает;
- `Tech Stack` — язык, фреймворки, сборка, тесты;
- `Architecture` — слои, модули, внешние системы;
- `Capabilities` — существующие возможности (пополняются из change-*);
- `Conventions` — код-стайл и договорённости.

Управляется скриптом, как и всё остальное:

```bash
# создать (LLM соберёт из твоего описания + стека из config.yaml):
./openspec.py --main "сервис уведомлений для интернет-банка, Kafka + Spring Boot"

# обновить (LLM получит старую версию и твои новые вводные):
./openspec.py --main "перешли на Kotlin, добавили модуль push-уведомлений"

# каркас без LLM:
./openspec.py --offline --main "описание проекта"
```

Главное: MAIN.md **автоматически подмешивается** в генерацию proposal,
spec-bdd, tasks и кода. Если хочешь «другое приложение» — меняешь
мейн-спеку и `config.yaml`, и весь конвейер пишет под него.

### 7.2 BDD-спека изменения (GIVEN-WHEN-THEN)

Спека изменения — сердце пайплайна. Формат каждого сценария:

```markdown
### S1: Успешное кодирование текста

- **GIVEN** сервер запущен, на вход подан текст "hello"      ← предусловия
- **WHEN**  выполняется GET запрос на /base64?text=hello     ← действие
- **THEN**  статус ответа 200, тело ответа равно "aGVsbG8="  ← проверяемый результат
```

Правила, которые скрипт передаёт модели (взяты из `.agent/schema.yaml`,
артефакт `spec-bdd`):

1. Строгий синтаксис **GIVEN — WHEN — THEN**.
2. **Все краевые случаи**: валидация, ошибки 400, 404, 500. Модель обязана
   описать не только happy path, но и что происходит при плохом вводе.
3. Каждому сценарию присваивается ID (`S1`, `S2`, ...) — по этим ID задачи
   в `tasks.md` ссылаются на сценарии.
4. В конце спеки — секция **OpenAPI Delta**: изменения контракта
   (paths, schemas) в YAML.

Смотри живой пример: [`specs/change-001-base64-echo/spec-bdd.md`](specs/change-001-base64-echo/spec-bdd.md) —
там 5 сценариев (happy path, кириллица, два случая 400, 500) и полная
OpenAPI-дельта.

Хочешь изменить правила генерации? Правь `.agent/schema.yaml` →
`artifacts` → `spec-bdd` → `rules`. Скрипт читает правила из YAML, ничего
перекомпилировать не нужно.

## 8. Offline-режим (без LLM)

Если LLM недоступен (нет ключа, нет интернета, хочется сделать всё руками):

```bash
./openspec.py --offline --new "хочу логирование запросов"
```

Скрипт создаст папку изменения и **каркасы всех трёх документов по
шаблонам** из `.agent/templates/` — с секциями и `TODO`-заглушками.
Дальше заполняешь вручную (или через AI-ассистента в IDE), и когда спека
готова — кодогенерацию можно запускать уже с LLM.

Offline-режим не требует даже библиотеки `requests` — только `pyyaml`.

Кодогенерация (`--codegen`) в offline-режиме **не поддерживается** —
для кода LLM обязателен.

## 9. Безопасность кодогенерации

Кодогенерация пишет файлы в твой проект, поэтому предусмотрено четыре уровня защиты:

1. **`--dry-run`** — показать список файлов без записи. Всегда начинай
   с него при первой работе с новой моделью.
2. **Подтверждение `[y/N]`** — перед записью скрипт показывает полный
   список файлов и ждёт подтверждения (обходится только явным `--yes`).
3. **Фильтрация путей** — записываются только относительные пути внутри
   проекта. Абсолютные (`/etc/passwd`) и с выходом наружу (`../../x`)
   отбрасываются с ошибкой в консоли.
4. **Диагностика** — сырой ответ модели на диск не пишется: при неудачном
   разборе его хвост печатается в терминал. Файлов-логов в `specs/` нет.

Скрипт **никогда не удаляет** файлы — только создаёт и перезаписывает.
Старую реализацию перед кодогенерацией коммить в git.

## 10. Конфигурация

Всё в `.agent/config.yaml` (показана реальная текущая конфигурация):

```yaml
project_context:
  tech_stack: "Java 17, Spring Boot 3.x, Maven, JUnit 5, MockMvc"  # уходит в промпт кодера
  code_style: "Conventional Commits, интерфейсы для контроллеров (API-first)"
  base_package: "com.example"     # базовый java-пакет для генерации

# Провайдер: активный профиль — ЕДИНСТВЕННЫЙ источник host / model / ключа
active_profile: "glm"        # --profile <name> переопределяет на один запуск

profiles:
  glm:                           # Z.AI Coding Plan (основной)
    base_url: "https://api.z.ai/api/coding/paas/v4"
    model: "glm-5.3"
    api_key_env: "ZAI_API_KEY"   # только env, не строкой в файле
    verify_ssl: false            # внутренний CA
  local:                         # локальная Ollama, когда VPN недоступен
    base_url: "http://localhost:11434/v1"
    model: "qwen2.5-coder:7b"
    verify_ssl: true

# Параметры запроса, НЕ зависящие от провайдера.
# base_url / model / ключа здесь быть не должно — они живут в профиле.
ai_settings:
  temperature: 0.2               # низкая — предсказуемые документы
  max_tokens: 30000
  timeout_seconds: 600           # в потоке считается МЕЖДУ кусками ответа
  stream: true                   # имена файлов печатаются по мере генерации
  # extra_params:                # произвольные параметры провайдера, см. ниже
  #   thinking:
  #     type: "disabled"

pipeline:
  isolate_git_branch: false      # true = --new всегда создаёт ветку spec/<id>
  auto_worktree: true            # кодоген сам заводит worktree изменению
  worktree_copy: []              # локальные файлы вне git → в новый worktree

code_generation:
  test_first: true               # тесты перед реализацией
  test_command: "mvn -q test"    # прогон тестов после записи файлов
  batch_size: 3                  # задач из tasks.md в один запрос к модели
  dependency_files: ["pom.xml"]  # файлы сборки в контекст (зависимости)

```

Что менять чаще всего:

- **Поменять модель** → одна строка `model:` (см. [«Как быстро поменять модель»](#3-установка)) или флаг `--model` разово.
- **Сменить провайдера LLM** → одна строка `active_profile:` (или `--profile` разово).
- **Другой стек** (Kotlin, Python, Node...) → `tech_stack` и `base_package`;
  промпты кодера подстроятся автоматически.
- **Хочешь ветку на каждое изменение** → `pipeline.isolate_git_branch: true`
  или флаг `--branch` разово.

### Ключи: только переменные окружения

В профиле указывается **имя переменной**, а не ключ:

```yaml
profiles:
  glm:
    api_key_env: "ZAI_API_KEY"     # ✔ так
```

```yaml
profiles:
  glm:
    api_key: "a26017db-...."           # ✘ так движок откажется работать
```

Вторая форма раньше поддерживалась «как альтернатива» — это была ошибка.
Получалось два способа задать одно и то же, и ключ незаметно уезжал
в репозиторий. Теперь движок падает с объяснением:

```
✖ В профиле 'glm' задан api_key прямо в config.yaml.
  Конфиг уходит в git — секрет из истории потом не убрать.
  Убери строку api_key и держи ключ в переменной окружения,
  имя которой указано в api_key_env.
```

Профиль **без** `api_key_env` (например `local` — локальная Ollama)
работает без ключа, это нормально.

Если имя переменной указано, а сама переменная пустая — движок
предупредит на старте, но запрос всё равно попробует отправить
(получишь `401` от шлюза):

```
⚠ Переменная ZAI_API_KEY не задана — запрос уйдёт без авторизации.
  Задать:  echo 'export ZAI_API_KEY="..."' >> ~/.zshenv
```

### `extra_params` — параметры провайдера без правки кода

Секция `ai_settings.extra_params` подмешивается **в тело запроса к API как
есть**. Движок её не разбирает и ничего о ней не знает — поэтому любую опцию
конкретного провайдера можно включить правкой конфига, не трогая
`cli.py`. Ключа нет — запрос уходит без дополнительных параметров.

```yaml
ai_settings:
  extra_params:
    thinking:
      type: "disabled"
```

При запуске движок печатает, что подмешал: `Доп. параметры запроса: thinking`.

**Зачем это нужно на практике — думающие модели.** GLM, o-серия OpenAI и
подобные сначала генерируют рассуждения (`reasoning_content`), и только потом
ответ. Бюджет `max_tokens` у них **общий** на то и другое. На тяжёлой задаче
модель может израсходовать весь лимит на размышления и вернуть **пустой
ответ** — движок сообщит «пустой ответ, вероятно весь max_tokens ушёл на
размышления» и остановит кодогенерацию.

Лечится одним из двух способов:

| Способ | Как | Когда |
|---|---|---|
| отключить размышления | `thinking: {type: "disabled"}` | кодогенерация по готовой спеке — думать почти не над чем |
| поднять лимит | `max_tokens: 80000` | сложная архитектура, качество важнее скорости |

Отключение размышлений заметно ускоряет генерацию, но на сложном рефакторинге
качество может просесть — придётся больше дожимать тесты руками.

Частые параметры:

| Параметр | Провайдер | Смысл |
|---|---|---|
| `thinking: {type: disabled}` | GLM (Z.AI) | выключить фазу размышлений |
| `reasoning_effort: low` | OpenAI o-серия | глубина рассуждений |
| `top_p`, `presence_penalty` | большинство | сэмплинг |
| `seed` | где поддерживается | воспроизводимая выдача |

Готовый закомментированный блок со всеми примерами лежит в
`.agent/config.yaml` — раскомментируй нужное.

## 13. Агентный режим: opencode + Superpowers

Движок можно гонять не только руками из терминала, но и **через ИИ-агента в
opencode** — в этом режиме агент (например, я в opencode) сам ведёт процесс:
уточняет идею, дёргает скрипты-тулы, ревьюит спеку, дожимает тесты.
Поверх навешан **Superpowers** — популярный open-source набор агентских
скиллов (MIT), который дисциплинирует агента: brainstorming перед работой,
строгий TDD, систематический дебаггинг, код-ревью.

### 13.1 Что где лежит (всё — внутри проекта, глобальный opencode не трогаем)

| Что | Где | Зачем |
|---|---|---|
| Superpowers (14 скиллов) | `.opencode/skills/<name>/` | инженерные привычки агента: brainstorming, TDD, debugging, ревью |
| Скилл `openspec-driver` | `.opencode/skills/openspec-driver/` | мостик: учит агента работать с движком |
| Команды `/openspec-new`, `/openspec-codegen` | `.opencode/command/*.md` | быстрый запуск шагов конвейера из чата |
| Движок | `.agent/` | сам конвейер (скрипт, схема, шаблоны) |

**Портативность — ключевая идея.** Весь тулкит = две папки: `.agent/` +
`.opencode/`. Скопировал их в любой проект → открыл там opencode →
скиллы, команды и движок работают, спеки (`specs/`) и код (`src/`)
создаются уже в том проекте. Ничего в глобальном `~/.config/opencode/`
не живёт и не должно.

```bash
# перенос в другой проект:
cd /path/to/другой-проект && openspec --init
```

> **⚠️ После копирования (и после любых правок скиллов) перезапусти
> opencode в целевом проекте** — скиллы и команды грузятся при старте.

### 13.2 Архитектура: скиллы + скрипты-тулы

```
ты в opencode: «хочу фичу X»
        │
        ▼
┌───────────────────────────────────────────────┐
│  Агент opencode (я)                           │
│  контекст: только НАЗВАНИЯ скиллов (~сотни    │
│  токенов). Тело скилла грузится по запросу —  │
│  это экономия токенов (progressive disclosure)│
│                                               │
│  скиллы: brainstorming → уточняет идею        │
│          openspec-driver → знает команды      │
│          test-driven-development → дожим код  │
└───────────────┬───────────────────────────────┘
                │ bash (единственный «инструмент»)
                ▼
     openspec --new "..."
                │  (вся тяжёлая работа ВНЕ сессии:
                │   промпты, ответы LLM, файлы)
                ▼
     specs/change-00N-.../  +  src/**.java
```

Почему это экономит токены: агент **не тащит в сессию** ни системные промпты
движка, ни ответы LLM, ни содержимое артефактов. Скрипт возвращает одну-две
строки («создан specs/.../spec-bdd.md»), агент читает спеку только на ревью.

### 13.3 Как этим пользоваться

**Вариант А — естественным языком.** Открой opencode в папке проекта и просто
проси: «хочу хэширование sha256» — скилл `openspec-driver` сработает сам:
агент уточнит детали → запустит `--new` → покажет резюме сценариев → после
твоего «ок» сгенерит код и дожмёт тесты по TDD.

**Вариант Б — командами проекта** (в папке `creator`):

```
/openspec-new хочу эндпоинт /hash?text=... в sha256
/openspec-codegen 2
```

**Вариант В — руками** (как в §4–§5) — никто не отменял.

### 13.4 Состав Superpowers (что установлено)

| Скилл | Что диктует агенту |
|---|---|
| `brainstorming` | перед любой фичей — уточнить намерение, предложить дизайн, дождаться одобрения |
| `writing-plans` / `executing-plans` | формат планов: требования → шаги → критерии проверки |
| `test-driven-development` | СТРОГО красный тест → минимальный код → зелёный → рефакторинг |
| `systematic-debugging` | гипотезы и изоляция, а не тыкание наугад |
| `requesting-code-review` / `receiving-code-review` | дисциплина ревью |
| `verification-before-completion` | не говорить «готово», пока не проверено |
| `subagent-driven-development` / `dispatching-parallel-agents` | параллельные субагенты |
| `using-git-worktrees` / `finishing-a-development-branch` | изоляция работы в worktree/ветке |
| `using-superpowers` / `writing-skills` | мета-скиллы про сами скиллы |

Полные тексты: [github.com/obra/superpowers](https://github.com/obra/superpowers) (MIT).

### 13.5 Управление установкой (всё внутри проекта)

```bash
# обновить Superpowers до свежей версии:
git clone --depth 1 https://github.com/obra/superpowers.git /tmp/sp
rm -rf .opencode/skills/brainstorming .opencode/skills/writing-plans  # ... и т.д.
for d in /tmp/sp/skills/*/; do rm -rf .opencode/skills/"$(basename $d)"; cp -R "$d" .opencode/skills/; done

# убрать Superpowers (openspec-driver и движок останутся):
cd .opencode/skills && rm -rf brainstorming dispatching-parallel-agents executing-plans \
  finishing-a-development-branch receiving-code-review requesting-code-review \
  subagent-driven-development systematic-debugging test-driven-development \
  using-git-worktrees using-superpowers verification-before-completion \
  writing-plans writing-skills

# убрать весь агентный слой (движок .agent/ продолжит работать из терминала):
rm -rf .opencode
```

После любых изменений — перезапуск opencode.

### 13.6 Связь с планом IDEA-плагина

Плагин возьмёт эти две папки как **payload**: `.agent/` (движок) +
`.opencode/` (скиллы и команды) будут зашиты внутрь плагина. При установке
плагина в IDEA он разложит их в проект автоматически — тот же перенос
копированием, только кнопкой «Install».

Два режима кнопок в плагине: **конвейер** → напрямую команда `openspec`
(быстро, детерминированно); **агент** → `opencode run --model
<провайдер/модель> "..."` как subprocess (своя сессия, можно несколько
параллельно — скиллы из `.opencode/` подхватятся, потому что лежат в
рабочей директории проекта). Профили `glm`/`local` из `config.yaml`
плагин унаследует автоматически.

## 14. Частые проблемы (Troubleshooting)

| Симптом | Причина и решение |
|---|---|
| `./openspec.py: No such file or directory` | Проект не развёрнут. Одна команда: `uvx --from git+https://github.com/MoshkaBortmanStar/creator.git@master openspec --init` |
| `Не найден uvx` | `brew install uv` (macOS/Linux), `winget install astral-sh.uv` (Windows) |
| `permission denied: ./openspec.py` | `chmod +x openspec.py`, либо запускай `python openspec.py ...` |
| `Не найден uvx` | `brew install uv` |
| `Это не проект OpenSpec` | В каталоге и выше нет `.agent/config.yaml`. Развернуть: `./openspec.py --init` |
| `Профиль не выбран` | В `config.yaml` нет `active_profile` и не передан `--profile`. Провайдер задаётся только профилем, дефолта нет |
| `LLM недоступна (...)` | Не поднята модель / неверный `base_url` в активном профиле / нет ключа. Частая причина у Z.AI — endpoint: у Coding Plan это `/api/coding/paas/v4`, а не `/api/paas/v4`. Или работай с `--offline` |
| LLM вернула пустые/обрезанные файлы | Увеличь `max_tokens` в конфиге, возьми модель-кодер побольше |
| `Отклонён небезопасный путь` при кодогенерации | Модель попыталась записать файл за пределами проекта — скрипт её остановил. Перегенерируй (`--codegen`) |
| `--change 1` → `не найдено` | Смотри точное имя: `--list`. Номер работает, если изменение с этим номером единственное |
| Кириллица в ID изменений | Так задумано: промпт транслитерируется (`эхо-сервис` → `eho-servis`) — ID остаются ASCII-безопасными для git и файловых систем |
| Скиллы Superpowers / команды `/openspec-*` не появляются | opencode грузит скиллы и команды только при старте — перезапусти opencode |

## Приложение: откуда это взялось

Реализация по ТЗ «Spec-Driven Change Development» (концепт OpenSpec /
Change Driver): CLI-движок в корне проекта, YAML-схема конвейера,
шаблоны артефактов, зашитые системные промпты для каждого шага и
